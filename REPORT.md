\# SRS №8 — Ограничения стека



\## 1. Цель работы



Изучить работу стека памяти Arduino Uno, исследовать последствия переполнения стека при рекурсии и сравнить рекурсивный и итеративный подходы. Дополнительно исследовать влияние больших локальных массивов на использование SRAM.



\## 2. Теоретические сведения



Arduino Uno на базе микроконтроллера ATmega328P имеет 2 КБ SRAM (2048 байт). SRAM используется для хранения статических данных, динамической памяти и стека.



Стек хранит данные активных вызовов функций: локальные переменные, адреса возврата и служебную информацию.



При глубокой рекурсии одновременно остаётся много активных вызовов функций. Каждый вызов занимает часть стека. Если доступной памяти становится недостаточно, программа может зависнуть, перезапуститься или начать работать неправильно.



\## 3. Предварительная оценка



Для приблизительной оценки используем формулу:



N ≈ (2048 − S − R) / F



Где:

\- S — объём статической памяти;

\- R — резерв памяти для других операций;

\- F — примерный размер одного кадра стека.



Точное значение зависит от компилятора, локальных переменных, служебных данных и используемых библиотек. Поэтому расчёт является приблизительным, а не точным пределом рекурсии.



В эксперименте использовалась рекурсивная функция с локальным массивом из 16 элементов типа `uint8\_t`. Только этот массив занимает 16 байт на один активный вызов, без учёта остальных расходов кадра стека.



\## 4. Эксперимент 1 — рекурсия



\### Предсказание



Ожидалось, что при увеличении глубины рекурсии свободная память стека будет уменьшаться. При достижении предела программа может перестать нормально работать или перезапуститься.



\### Результаты



\- Последняя достоверно увиденная контрольная отметка глубины: 10.

\- Наблюдаемое поведение: после начала выполнения программы Serial Monitor показывал повторяющиеся сообщения `START`.

\- Повторение сообщения указывает на повторный запуск программы и является признаком возможного сбоя при глубокой рекурсии.

\- Точная максимальная глубина рекурсии не установлена.



\### Сравнение оценки и результата



Наблюдаемое поведение соответствует предположению о возможном переполнении стека. Точную глубину нельзя определить только по последней выведенной отметке, поскольку программа могла продолжать выполнение между сообщениями.



Результат может отличаться от расчёта из-за размера реального кадра функции, статической памяти программы и служебных расходов библиотек.

\## 5. Эксперимент 2 — итеративный алгоритм



Вместо рекурсии использовался цикл `for`, выполняющий 10001 итерацию.



\### Ожидаемый результат



Программа должна дойти до 10000 и вывести `SAFE FINISH`. В отличие от рекурсии, цикл не создаёт цепочку одновременно активных вызовов функций, поэтому использование стека остаётся примерно постоянным.



\### Фактический результат



Эксперимент завершился успешно. В Serial Monitor были выведены значения от 0 до 10000 с шагом 1000, после чего появилось сообщение `SAFE FINISH`.



Переполнения стека не наблюдалось.



Таким образом, итеративный алгоритм позволил выполнить все повторения без постоянного увеличения глубины стека.



Скриншот: `screenshots/safe\_result.png`



\## 6. Эксперимент 3 — Memory Hog



Функция выделяет локальный массив из 300 элементов типа `int`.



На Arduino Uno тип `int` занимает 2 байта. Поэтому один массив занимает:



300 × 2 = 600 байт.



При вложенных вызовах функции массивы нескольких активных вызовов одновременно занимают память.



\### Результаты



| Уровень | Количество активных вызовов | Суммарный размер массивов | Фактический результат |

|---:|---:|---:|---|

| 0 | 1 | 600 байт | PASS |

| 1 | 2 | 1200 байт | PASS |

| 2 | 3 | 1800 байт | Повторный запуск программы |

| 3 | 4 | 2400 байт | Не проверялся |

| 4 | 5 | 3000 байт | Не проверялся |



При уровне 0 программа успешно вывела `MEMORY HOG FINISH`.



При уровне 1 программа также завершилась успешно и вывела сообщения для уровней 1 и 0.



При уровне 2 вместо нормального завершения наблюдалось многократное повторение `MEMORY HOG START`. Это указывает на повторный запуск программы и возможное исчерпание доступной памяти.



Уровни 3 и 4 не проверялись, поскольку на уровне 2 уже наблюдалось нестабильное поведение.



Важно: приведённые значения показывают только размер локальных массивов. Дополнительно SRAM используется программой, глобальными переменными, стеком и другими служебными данными.



Скриншот: `screenshots/memory\_hog\_result.png`



\## 7. Инженерный вывод



В ходе работы было исследовано влияние глубины вызовов функций на использование оперативной памяти Arduino Uno. Эксперимент с рекурсией показал повторные запуски программы при глубоком вызове функции. Итеративный алгоритм успешно выполнил 10001 итерацию и завершился без наблюдаемого переполнения стека. В эксперименте Memory Hog уровни 0 и 1 завершились успешно, а на уровне 2 наблюдались повторные запуски программы. Это показывает, что большие локальные массивы во вложенных функциях могут быстро исчерпать доступную SRAM. В системах управления БПЛА необходимо контролировать использование памяти, ограничивать глубину вызовов функций и предусматривать безопасную обработку ошибок.
